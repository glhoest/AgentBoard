# Claude: implement the AgentBoard interface

Implement the human-facing interface for this project. Read `README.md` and `agentboard.ts` first; their data contract, validation, locking and API are authoritative. Do not change the schema or invent endpoints. Deliver one self-contained `board.html` next to `agentboard.py`, plus UI tests if practical. No build step, remote assets, CDN, external services or database. Preserve the CLI.

Build a polished, practical, responsive Kanban board for humans collaborating with agents. Show configured columns and cards with title, ID, priority, labels, assignee and completion count. Offer a detail editor for all writable fields: title, status, priority, assignee, labels, description, acceptance criteria with completion toggles, notes and archive state. Allow creating cards; moving via drag and drop plus an accessible keyboard/touch status control; changing assignee; archiving and viewing/restoring archived cards. Add search/filtering, counts, loading/empty/error states and keyboard/focus handling. Use explicit save/cancel and preserve unsaved drafts.

Primary mode is the local bridge: `bun agentboard.ts --root /path/to/project serve --ui /path/to/board.html`. Read the token from `#token=...` and send `Authorization: Bearer <token>` on every API call. Show launch instructions if missing. Use only documented `GET /api/board`, `POST /api/items`, `PATCH /api/items/:id`. Include the last observed revision and exact item hash from the snapshot in every update. Compare hashes as well as revisions when polling, including external edits which do not update the revision. After creation or a successful patch, fetch a fresh snapshot before the next update to obtain the current hash. Poll every 1–2 seconds and on focus, back off on errors and resume automatically; show connection status. CLI changes must appear without manual refresh. If an item being edited changes, preserve the draft and flag a conflict. On any detected change while editing or HTTP 409, warn the user and retain the entire draft in memory. Offer to keep editing the draft or reload the current item, explicitly confirming before discarding the draft; provide copy-draft access. Do not promise automatic diff or merge in v1 and never silently overwrite. Dragging must use the latest revision and handle races. Claims do not prevent other edits.

Optionally support opening HTML directly and selecting `.agentboard` through the File System Access API with the same schema and polling. This supplements the bridge. Direct browser writes cannot participate in the advisory lock or offer atomic compare-and-swap: visibly warn about possible lost concurrent updates. Check revision before save but do not present that as a guarantee. Detect unsupported browsers and explain bridge fallback. Do not require folder access in bridge mode; do not claim direct `file://` support without testing.

Treat all card text/JSON as untrusted: no raw `innerHTML` from data; sanitize Markdown correctly or display plain text. Use relative API URLs; don't leak token via logs, external requests, referrers or DOM. Show invalid data and missing columns visibly. Never write board files directly in bridge mode. Preserve unchanged fields. Server snapshots include archived items; hide them by default. Save criteria as the whole `{text,done}` array and labels as unique strings. Don't invent manual ordering; v1 has no order field. Handle long content.

Verify with a temporary initialized project: create/edit in UI; create/move/edit with CLI and confirm refresh; provoke conflict and confirm draft survives; check archive/restore, keyboard, desktop/narrow layouts and reconnect. Run the existing tests (bun test). State exactly what you tested and limitations; do not invent browser test results.
